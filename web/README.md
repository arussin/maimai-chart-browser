# Browser source ownership

The hosted browser and standalone HTML use one application graph. The existing DOM
and styles are preserved. There is no framework runtime or parallel classic application.

## Entry and state ownership

| Module | Owns | Does not own |
| --- | --- | --- |
| `browser-entry.ts` | Hosted startup and memoized application loading | Page-specific state |
| `browser-offline.ts` | Embedded configuration/data and disabled usage adapter | A separate application |
| `application.ts` | One composition of factories and explicit dependencies | Rendering algorithms |
| `runtime/navigation.ts` | Route intent, metadata, language transitions and committed activation | Player records |
| `runtime/history.ts` | Native history writes and traversal/hash subscriptions | Application decisions |
| `runtime/browser-state.ts` | Public filters, requested sorts, row/compare/similarity choices, disclosures and validated snapshots | Scores, source connections or credentials |
| `runtime/position.ts` | Readiness-dependent, cancellable focus/scroll restoration | A second control snapshot |
| `runtime/import-coordinator.ts` | Private session readiness, consent transactions, commit/rollback, refresh and cross-tab invalidation | DOM rendering |
| `runtime/player-session-browser.ts` | Browser I/O and report handoff transport for the private owner | Retained application decisions |
| `runtime/catalog.ts` | Verified release selection and disposable detail hydration | Mutation of canonical catalog data |
| `runtime/verified-data.ts` | Bounded same-origin reads and single/multipart integrity | Provider imports |
| `usage-contract.ts` / `usage.ts` | Finite broad events and bounded ephemeral batches | URLs, chart IDs, search text or player state |

The DOM factories under `src/views/` retain established markup and interaction logic.
Their public controls reference the **same** BrowserState sets/objects; they must not
allocate a replacement controller. A restore commits validated public settings before
asking the view to render. Requested personal sorts survive delayed private readiness.
A later trusted interaction cancels pending position work, and a later navigation
intent prevents an earlier fetch from committing.

The pure catalog/player/matching functions accept data and return projections or
results. They cannot import a browser adapter or use DOM, persistence or fetch globals.
The existing DOM factories are JavaScript; strict TypeScript applies to the maintained
runtime boundaries and finite contracts, not retrospectively to every view body.

## Generated distributions

Run the pinned build in an approved disposable dependency workspace. `build.mjs`
produces hosted ES modules, one self-contained offline bundle, and the small classic
entry adapters still used by other published tools. Those adapters call the maintained
factories; they are not a second maintained implementation. `browser-assets.json`
records the exact module closure, hashes and retired application filenames. The Python
builder and publisher use the same validator for that closure.

Do not edit generated JavaScript. Do not restore retired application scripts to satisfy
an old test. Update a test to the real module interface, or use a documented external
compatibility entry when the external contract is what the test verifies.

## Required checks

- Strict TypeScript, including negative compile cases in `tests/type-contracts.ts`.
- `check-architecture.mjs`: acyclic imports, pure-domain boundaries, single public/private
  owners, native history ownership, singleton factory composition and no legacy service globals.
- `build.mjs --check`: generated bytes and dependency manifest match authored source.
- Unit tests for state validation, delayed/stale operations, private rollback and telemetry.
- Isolated browser behavior plus exact-pixel comparisons on the retained same-data baseline.
- The standalone `file:` test must make no neighboring-file or network requests.

Functional browser specs import `tests/browser/fixtures.js`. Its compatibility names are
**test-only** and are installed after the application has mounted. Tests must await that
readiness when they call a module through the harness. The separate performance and
native lifecycle harnesses use their own default-deny transport with no cache-changing
request interception.

## Repeatable visual comparison

`tests/browser/architecture.config.js` defines Chromium, Firefox and WebKit. Each
engine captures eight existing interaction states in four languages at 320, 768 and
1280 pixels: 288 comparisons. It records browser/OS versions, computed font families,
and resolved platform-font information where the engine exposes it; absence is explicit.
Use the same operating system, installed fonts and pinned browser builds for both sides.

In a disposable browser test workspace, set `PYTHON`, `PLAYWRIGHT_BROWSERS_PATH`,
`MAIMAI_TEST_PORT`, `MAIMAI_BROWSER_OUTPUT` and `MAIMAI_VISUAL_BASELINE`. Run
`node node_modules/@playwright/test/cli.js test --config=architecture.config.js --update-snapshots`
against the reviewed baseline output. Then change only `MAIMAI_BROWSER_OUTPUT` to the
candidate with the **identical catalog/artwork fixture data** and run the same command
without `--update-snapshots`. Retain both reports and the hashes of data, runtime assets,
styles and relevant system font files. A newly generated fixture with different public
identities is not a valid comparison input. No Linux visual result is implied by Windows
captures; Linux reproduction requires its own same-platform baseline.
