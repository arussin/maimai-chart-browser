## Visitor flow

The “Support maimai.party” button sits beside “View on GitHub” in About, outside the credits footer. It shares the GitHub button's sizing and shape, with a white background, black border/text and a filled heart with discrete bands of the five site-logo colors (selected option B). A small “Powered by Stripe” line below the button uses Stripe’s official wordmark. It opens a white dialog with the site's official wordmark and the invitation “maimai.party is free for everyone. If you’d like to help with hosting and domain costs, a few dollars is more than enough.” The logo and introduction sit directly above Stripe's full embedded Checkout. Stripe owns the editable amount, payment controls and provider attribution. See [branding provenance](support-branding.md).

The owner-provisioned Stripe Price uses customer-chosen pricing with a USD base: $5 suggested, no site-defined minimum, $100 maximum. Leave the optional `custom_unit_amount.minimum` unset. Stripe's own processing floor still applies (currently $0.50 for USD; converted charges must meet the settlement-currency minimum). The Worker verifies the suggestion, cap and absent minimum before creating a session. Adaptive Pricing is requested so eligible sessions can present and charge in the visitor's local currency; Stripe controls currency selection, conversion and the final total. It currently includes a 2–4% conversion fee in the local-currency rate; visitors can choose the original USD currency instead. The real-provider observations are recorded separately; a local mock cannot establish which methods Stripe renders. References: [native customer-chosen amounts](https://docs.stripe.com/payments/checkout/pay-what-you-want.md?payment-ui=embedded-page), [processing floors](https://docs.stripe.com/currencies#minimum-and-maximum-charge-amounts), [Adaptive Pricing](https://docs.stripe.com/payments/currencies/localize-prices/adaptive-pricing?payment-ui=embedded-page), [conversion fees](https://support.stripe.com/questions/adaptive-pricing).

Closing the dialog leaves its payment unfinished. Reopening or retrying resumes the same attempt; after a page refresh, an explicit open resumes it. Stripe's native field lets the visitor edit the amount in that same session. Completed/expired checkouts offer an explicit new attempt. A declined card remains in Stripe's form so the visitor can choose another method. Errors offer retry without linking to another payment provider.

Card completion is confirmed through the server before showing thanks. Redirect methods use the fixed `/support-return.html` page. Pending payments say they are processing, rather than displaying success or encouraging another payment. An unrecognized return never claims success. The page uses this tab's saved checkout reference, so no session ID, client secret, payer details or completion flags are needed in its URL. If browser storage is unavailable, checkout does not start and explains how to retry.

Imported results kept only in application memory can be lost when a wallet navigates away. The payment code never reads player storage or copies results to payment metadata. The dialog relies on Stripe's own payment attribution; the extra attribution and Payment details dropdown were removed at the owner's request.

## Components and API contract

- `src/maimai_intelligence/assets/support-config.js`: public feature flag, publishable key and site wording. Enabled for the configured live origin; disabling the flag hides Support. Only the exact configured HTTPS origin is eligible; unsupported origins, local files and HTTP keep the support button hidden.
- `support-client.js`: same-origin requests and payment-only tab storage (`support.checkout.v2.maimai-party`), accepted for at most 23 hours. No amount, currency, client secret or payer details are persisted. The earlier v1 draft was never deployed.
- `support-stripe.js`: lazy native dialog, SDK lifecycle, focus restoration and retry/return handling. There is no secondary provider: disabled or absent Stripe configuration hides support, and an active Stripe dialog offers retry on failure.
- `support-return.html` / `.js`: dedicated no-analytics status page. Meta and release-header CSP allow only local scripts/connections, blocking injected Cloudflare beacons. Both Pages' extensionless path and `.html` path receive the restrictive headers.
- `support-worker/index.mjs`: dependency-free Worker using web-standard APIs, provisioned separately from the static site. It is not included in the public release allowlist or updater deployment. No webhook, database, player account or fulfillment is introduced.

| Endpoint | Accepted JSON | Successful response |
| --- | --- | --- |
| `POST /api/support/checkout` | `project`, random UUIDv4 `attempt`, optional known `session` when resuming | `status`, `session`, plus `clientSecret` only when open |
| `POST /api/support/status` | `project`, `attempt`, `session` | `status` only: `open`, `paid`, `pending`, `expired` |

The server owns the project allowlist, product name, origin, return path, USD base currency and amount bounds. It retrieves the configured `SUPPORT_PRICE_ID` with its product and currency options, and requires an active one-time customer-chosen Price, matching mode/product/currency and exact preset/maximum and an unset optional minimum. Explicit non-USD currency options fail closed; this flow delegates localization to Adaptive Pricing. Stripe enforces the validated bounds in its own form. The Worker rejects client-supplied amounts, extra input fields, cross-origin requests, missing provisioning, mismatched live/test credentials and malformed or oversized bodies. Reads and upstream calls have deadlines; responses are `no-store`. The original random attempt is a capability held in the tab; Stripe metadata contains its SHA-256 digest and the fixed project ID. Status retrieval verifies this digest and project, session and mode before returning anything. Client callbacks and URL parameters cannot certify a payment.

The Stripe idempotency key depends on project and attempt, not on amount or time. Initial retries use an identical creation request. Once the client knows its session ID, reopening retrieves that session and validates its ownership instead of recreating it, so later deployment-setting changes do not invalidate a known checkout. Amount changes remain inside Stripe. There is no persistent local payer identity or application request/body logging. A required Cloudflare rate-limit binding bounds anonymous traffic; it is transient, per Cloudflare location, and not a global accounting control. Shared public IPs may receive a temporary retry message. Origin checks limit browser misuse, not determined non-browser clients.

Server API version is pinned to `2026-08-26.dahlia`; the browser uses `https://js.stripe.com/dahlia/stripe.js` and `createEmbeddedCheckoutPage`. The request uses `ui_mode=embedded_page`, `redirect_on_completion=if_required`, a single reusable customer-chosen Price at quantity 1, Adaptive Pricing and a support-specific payment-method configuration. It does not set a hard-coded payment-method list, create a recurring subscription or attach player data. See [Stripe's integration guide](https://docs.stripe.com/payments/accept-a-payment?payment-ui=checkout&ui=embedded-page), [API versioning](https://docs.stripe.com/api/versioning) and [redirect behavior](https://docs.stripe.com/payments/checkout/custom-success-page?payment-ui=embedded-page).

There is no fulfillment or entitlement to deliver. Stripe Dashboard is the financial record. Analytics/return visits are incomplete observations and must never be used as a payment ledger. Add verified webhook handling before introducing fulfillment or durable payment accounting.
